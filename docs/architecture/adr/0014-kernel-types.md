# 0014. Kernel types: catálogo vocabulary that cannot hold an invalid value

- **Status**: Accepted
- **Date**: 2026-10-10
- **Deciders**: Founding maintainer
- **Issue**: [#19](https://github.com/sebalvarado/caudal-sip/issues/19), part of [#17](https://github.com/sebalvarado/caudal-sip/issues/17)

## Context

[ADR-0012](0012-crate-boundaries.md) puts the vocabulary every domain shares in one crate, `types`, and limits it to what the catálogo defines: money, BIC, the payment's identifier, payment state, reason code, and llave type. A change to `types` rebuilds everything, so the set stays small. This record fixes the shape of each type. Every agent will build against these types, so they have to be right before the first domain crate exists.

Two facts from the sources shape the record. The catálogo's unique payment code is `PmtId/InstrId`, generated by the ordering integrante (Catálogo Operacional §7, §8). Our earlier docs called it the "end-to-end id", but `EndToEndId` is a separate ISO field that the catálogo gives no rule for. And the worked example in [`posting-patterns.md`](../posting-patterns.md) carried a tax of `0.0375`, while [`fees.md`](../fees.md) says the ledger stores integer cents. Only one of those can be true.

## Decision

Every kernel type is a newtype or an enum with private fields. The only way to get a value is a constructor that validates it, so a value that exists is valid. Nothing in the kernel does I/O or reads a clock.

**`Usd`** is a non-negative amount in integer cents. It has no float constructor and no `Add` that can wrap or panic. Arithmetic is `checked_add` and `checked_sub`, which return `None` on overflow or on going below zero, and the caller refuses the operation. Parsing a decimal string accepts at most two decimals. A third decimal is an error, not something to round: rounding happens once, in `fees` ([`fees.md`](../fees.md)). Zero is a valid `Usd`, because a free tier is a real fee. A zero *payment* is the catálogo's `AM01`, and `payments` checks for it. Signed balances and the headroom unit are not money in general, so they live in `ledger` ([ADR-0011](0011-rust-monorepo.md): `Usd` is distinct from headroom).

**`Bic`** is the BCE-assigned code of an integrante or a red: up to 11 uppercase ASCII letters and digits (Catálogo Operacional §3, note 2). We do not enforce ISO 9362's eight-or-eleven rule, because the BCE's own reports use shorter codes. Integrante and red BICs share the type, and the field a BIC sits in says which role it has.

**`PaymentId`** is the catálogo's unique payment code, and it holds the ordering integrante's `Bic`. It is built from the ordering BIC and the raw code. The constructor checks what the catálogo defines: 20 to 35 characters, the ordering BIC first, then 14 digits of date and time (Tabla 14). Anything finer waits for the catálogo técnico. Because the value carries its own BIC, the pair (ordering BIC, payment id) that keys a payment network-wide is one value. A key whose BIC disagrees with the code cannot be built. `EndToEndId` is carried as evidence and keys nothing.

**`PaymentState`** has exactly the six states of Tabla 11: `Rcvd`, `Actc`, `Acsp`, `Acsc`, `Rjct`, `Pdng`. Each one renders as the catálogo's code. There is no `Unknown` variant, and a state the catálogo does not list does not parse. The type is a value read from the projection, never a column the payment stores ([ADR-0013](0013-ledger-is-the-aggregate.md)). Which transitions are legal belongs to `payments`, not the kernel. `Pdng` keeps the catálogo's name while its meaning is an open question to the BCE. An irrevocable payment with an unknown outcome (exception 3) is `Acsp` plus a reconciliation item, not `Pdng` ([`posting-patterns.md`](../posting-patterns.md) §2.1).

**`ReasonCode`** has exactly the 21 codes of Tabla 12. Each one carries its ISO code, the catálogo's internal `02xx` code where Tabla 12 gives one, and the party Tabla 12 holds responsible. It is the only reason type our code can emit. A code received from a counterparty is a **`ReceivedReason`**: either `Listed(ReasonCode)` or `Unlisted(code)`, where an unlisted code is any four uppercase ASCII letters or digits. An unlisted reason is kept as evidence, and the rejection still stands. We never invent a code, and we never discard one a counterparty sent.

**`LlaveType`** has the four types of Tabla 1, each rendering as its code: `Celular` `0001`, `Identificacion` `0002`, `Correo` `0003`, `Alfanumerico` `0004`. The llave *value* and its format rules belong to `directory`, which owns `Llave`.

**Not in the kernel**, because one domain owns each of them: `AccountId` and the headroom unit (`ledger`); `Llave`, `Credencial`, and `MaskedName` (`directory`). A resolution response can carry only a `MaskedName`, and the only way to make one is to mask a full name. The type fixes *that* names are masked. *How* they are masked is a llave rule, so it belongs to the directory privacy RFC already in the observations register ([`../../rfcs/README.md`](../../rfcs/README.md)). Until that RFC, the default keeps the first given name and the initial of every other name **[proposal]**. The catálogo only requires that the payer sees the beneficiary's name (§5, rule 1).

The [glossary](../../glossary.md) maps each term to its type.

## Alternatives considered

- **`rust_decimal` or another decimal type for money.** Rejected. The scheme settles in cents. A decimal type makes a sub-cent amount representable, and that is exactly the bug the integer rules out.
- **A signed `Usd`.** Rejected. Amounts in this scheme are never negative. Direction lives in debit and credit, and a balance is a ledger concept with its own type.
- **`ReasonCode` with an `Other(String)` variant.** Rejected. Our code could then emit an invented code. Keeping received evidence in a separate type gives the same tolerance on the inbound side without that hole.
- **Separate `IntegranteBic` and `RedBic` types.** Rejected for now. The catálogo uses one code format for both, and the struct field already says which role a BIC has. Revisit if mixing them up shows up in review.

## Consequences

Easier: a sub-cent amount, an invented reason code, or a payment key with mismatched parts does not compile or cannot be built. Agents can write property tests against constructors with a known contract.

Harder: every boundary parses into these types and handles the error. The worked example in [`posting-patterns.md`](../posting-patterns.md) is corrected to whole cents.

Committed: the kernel holds these six concepts and nothing else until a new record adds one. The calendar type of [ADR-0017](0017-time-calendar-identifiers.md) is the only addition so far. A catálogo revision that adds a state or a code is a kernel change, made deliberately.
